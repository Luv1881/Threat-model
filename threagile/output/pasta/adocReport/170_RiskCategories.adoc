[[undocumented-entry-point]]
== [.ElevatedRisk]#Stage III - Undocumented Application Entry Point: 5/5 unmitigated Risks#

*Description* (Elevation of Privilege): https://cwe.mitre.org/data/definitions/693.html[CWE 693]::
PASTA Stage III requires decomposing the application into entry points so that threats can be mapped against known attack surfaces. A technical asset reachable from the internet or marked as internet-exposed that has no entry_point_type declared represents an undocumented entry point that cannot be systematically analysed for threats.


*Impact*::
Undocumented entry points are excluded from threat analysis, leaving unknown attack surface that attackers can exploit without detection or mitigation.


*Detection Logic*::
In-scope technical assets marked internet=true or reachable from an internet trust boundary that do not have an entry_point_type field declared.


*Risk Rating*::
Medium baseline; elevated when the asset processes sensitive data or requires no authentication.


[RiskStatusFalsePositive]#*False Positives*#::
[RiskStatusFalsePositive]#Internal infrastructure assets (databases, caches) that happen to be reachable across a network perimeter but are not themselves application entry points.
#

[RiskStatusMitigated]#*Mitigation*# (Architecture): Document all application entry points::
Declare entry_point_type on every internet-exposed technical asset (api, web_ui, cli, file_upload, webhook, cron, or internal_rpc). Maintain an entry point register and review it as part of each release cycle.



* [RiskStatusMitigated]#ASVS Chapter#: https://owasp.org/www-project-application-security-verification-standard/[V1 - Architecture, Design and Threat Modeling Requirements]
* [RiskStatusMitigated]#Cheat Sheet#: https://cheatsheetseries.owasp.org/cheatsheets/Attack_Surface_Analysis_Cheat_Sheet.html[Attack_Surface_Analysis_Cheat_Sheet]

[[per-operation-rate-limiting-missing]]
== [.ElevatedRisk]#Stage V - Custom-Developed Service Without Per-Operation Rate Limiting: 2/2 unmitigated Risks#

*Description* (Denial of Service): https://cwe.mitre.org/data/definitions/770.html[CWE 770]::
PASTA Stage V identifies vulnerabilities in the attack surface. Custom-developed services that process authentication credentials or session tokens and have outgoing communication links without rate limiting are vulnerable to credential stuffing, brute-force, bulk data exfiltration, and resource exhaustion. Global API rate limits are too coarse to prevent targeted abuse of individual high-value operations such as login, password reset, or bulk data exports.


*Impact*::
Attackers can enumerate users, brute-force credentials, bulk-download sensitive data, or exhaust backend resources by sending unlimited requests to unthrottled operations. Business process integrity degrades when operations can be repeated without throttling.


*Detection Logic*::
In-scope custom-developed process-type technical assets that process authentication data (user-credentials or session-tokens) and have at least one outgoing communication link where rate_limited is false and usage is not devops.


*Risk Rating*::
Medium baseline. Elevated for assets with internet-exposed entry points or those processing strictly-confidential authentication credentials.


[RiskStatusFalsePositive]#*False Positives*#::
[RiskStatusFalsePositive]#Internal service-to-service links that are not reachable from untrusted callers, or where rate limiting is enforced by an upstream proxy (e.g., Nginx limit_req). Set rate_limited: true on the link or change usage to devops to suppress.
#

[RiskStatusMitigated]#*Mitigation*# (Operations): Add per-operation rate limiting to all communication links in the authentication and data flow paths::
Apply rate limiting at the operation level using token-bucket or sliding-window algorithms, enforced per-user for authenticated requests and per-IP for unauthenticated requests. Set rate_limited: true on every communication link once per-operation limits are implemented and verified.



* [RiskStatusMitigated]#ASVS Chapter#: https://owasp.org/www-project-application-security-verification-standard/[V4 - Access Control Verification Requirements]
* [RiskStatusMitigated]#Cheat Sheet#: https://cheatsheetseries.owasp.org/cheatsheets/Denial_of_Service_Cheat_Sheet.html[Denial_of_Service_Cheat_Sheet]

Is rate_limited set to true on every communication link that participates in authentication or sensitive data processing? Are per-user limits enforced in addition to any global API limits?

[[no-rate-limiting-public-api]]
== [.ElevatedRisk]#Stage V - No Rate Limiting on Internet-Exposed API: 1/1 unmitigated Risk#

*Description* (Denial of Service): https://cwe.mitre.org/data/definitions/770.html[CWE 770]::
PASTA Stage V identifies weaknesses that enable exploitation. An internet-accessible API endpoint without rate limiting is vulnerable to brute-force credential attacks, credential stuffing, API abuse, and denial-of-service amplification. Rate limiting is a fundamental control for any internet-exposed API.


*Impact*::
Brute-force attacks against authentication endpoints, mass data harvesting via enumeration, DDoS amplification, and billing abuse on pay-per-use endpoints.


*Detection Logic*::
In-scope technical assets with entry_point_type of api or web_ui that receive communication links from internet-exposed assets where rate_limited is false.


*Risk Rating*::
Elevated for authentication endpoints; medium for general data APIs. High when the API has no authentication at all.


[RiskStatusFalsePositive]#*False Positives*#::
[RiskStatusFalsePositive]#Internal APIs behind a WAF or API gateway that provides rate limiting at the infrastructure layer; document and mark rate_limited as true on the comm links.
#

[RiskStatusMitigated]#*Mitigation*# (Operations): Implement rate limiting on all internet-exposed API entry points::
Add rate limiting at the API gateway or application layer (token bucket, sliding window). Apply stricter limits on authentication endpoints. Set rate_limited to true on the corresponding communication links after implementation.



* [RiskStatusMitigated]#ASVS Chapter#: https://owasp.org/www-project-application-security-verification-standard/[V4 - Access Control Verification Requirements]
* [RiskStatusMitigated]#Cheat Sheet#: https://cheatsheetseries.owasp.org/cheatsheets/Denial_of_Service_Cheat_Sheet.html[Denial_of_Service_Cheat_Sheet]

[[weak-auth-on-entry-point]]
== [.ElevatedRisk]#Stage VI - Weak Authentication Strength on Internet-Exposed Entry Point: 1/1 unmitigated Risk#

*Description* (Spoofing): https://cwe.mitre.org/data/definitions/287.html[CWE 287]::
PASTA Stage VI models how attackers simulate attacks against identified entry points. Internet-exposed entry points with weak authentication (none or password-only) are prime targets for credential stuffing, phishing, and account takeover attacks. High-value or sensitive entry points should require MFA or hardware tokens.


*Impact*::
Full account takeover, lateral movement into internal systems, and data exfiltration. Credential stuffing attacks against password-only endpoints succeed at statistically predictable rates given leaked credential databases.


*Detection Logic*::
Internet-exposed technical assets classified as entry points where requires_authentication_strength is not mfa or hardware and the asset handles confidential or strictly-confidential data.


*Risk Rating*::
High for entry points storing or processing strictly-confidential data with no MFA. Elevated for confidential data with password-only authentication.


[RiskStatusFalsePositive]#*False Positives*#::
[RiskStatusFalsePositive]#Public APIs serving non-sensitive, non-authenticated data (e.g., public search) do not require strong authentication; ensure confidentiality is set to public.
#

[RiskStatusMitigated]#*Mitigation*# (Architecture): Strengthen authentication on all internet-exposed entry points::
Require MFA for all user-facing internet entry points handling sensitive data. Declare requires_authentication_strength as mfa or hardware on the technical asset. Consider phishing-resistant authentication (WebAuthn, FIDO2) for high-value assets.



* [RiskStatusMitigated]#ASVS Chapter#: https://owasp.org/www-project-application-security-verification-standard/[V2 - Authentication Verification Requirements]
* [RiskStatusMitigated]#Cheat Sheet#: https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html[Authentication_Cheat_Sheet]

[[internet-reachable-datastore]]
== [.ElevatedRisk]#Stage VII - Internet-Reachable Datastore With No Mitigation: 2/2 unmitigated Risks#

*Description* (Information Disclosure): https://cwe.mitre.org/data/definitions/284.html[CWE 284]::
PASTA Stage VII evaluates residual risk. A datastore (database, cache, object store) that can be reached from the internet, either directly or via a chain of HTTP/plain protocol hops, with no network segmentation represents one of the highest-risk configurations in any architecture. Attackers who compromise any internet-facing component gain a direct path to sensitive stored data.


*Impact*::
Mass data exfiltration of all stored records, ransomware encryption of datastores, complete loss of data integrity, and regulatory breach notification obligations.


*Detection Logic*::
In-scope datastore technical assets that have any incoming communication link originating from an internet-exposed technical asset.


*Risk Rating*::
Critical when the datastore holds strictly-confidential data; high otherwise.


[RiskStatusFalsePositive]#*False Positives*#::
[RiskStatusFalsePositive]#Edge datastores intentionally internet-accessible (e.g., CDN origin) with documented justification, no sensitive data, and comprehensive access controls.
#

[RiskStatusMitigated]#*Mitigation*# (Architecture): Segment datastores from internet-facing components::
Place all datastores in a dedicated backend trust boundary with no direct internet access. Ensure all communication links between internet-facing assets and datastores go through the application tier (no direct datastore exposure). Apply defense-in-depth with connection-level authentication and network ACLs.



* [RiskStatusMitigated]#ASVS Chapter#: https://owasp.org/www-project-application-security-verification-standard/[V1 - Architecture, Design and Threat Modeling Requirements]
* [RiskStatusMitigated]#Cheat Sheet#: https://cheatsheetseries.owasp.org/cheatsheets/Database_Security_Cheat_Sheet.html[Database_Security_Cheat_Sheet]

[[missing-threat-scenario]]
== [.LowRisk]#Stage I - No Threat Scenarios Defined for Internet-Exposed Entry Points: 1/1 unmitigated Risk#

*Description* (Elevation of Privilege): https://cwe.mitre.org/data/definitions/693.html[CWE 693]::
PASTA Stage I defines business and security objectives and maps them to threat actors. An architecture with internet-exposed entry points but no documented threat scenarios means that adversarial thinking has not been applied: the team has not specified who might attack, how, and with what capabilities.


*Impact*::
Without explicit threat actor profiles and attack scenarios, mitigations are chosen reactively rather than proactively, leaving systematic threat actor capabilities unaddressed.


*Detection Logic*::
Internet-exposed technical assets with a declared entry_point_type but no matching threat scenario that lists them as an entry asset.


*Risk Rating*::
Low severity from a technical standpoint but indicates a process gap that increases risk of systematic coverage omissions.


[RiskStatusFalsePositive]#*False Positives*#::
[RiskStatusFalsePositive]#Models in early development where threat scenario documentation is tracked externally in a threat register; provide a reference in the management summary.
#

[RiskStatusMitigated]#*Mitigation*# (Operations): Define threat scenarios for all internet-exposed entry points::
Add a threat_scenarios section to the model with at least one scenario per distinct threat actor type (e.g., script-kiddie, insider, nation-state). Each scenario should document entry_assets, kill_chain_steps, and mitigated_by controls.



* [RiskStatusMitigated]#ASVS Chapter#: https://owasp.org/www-project-application-security-verification-standard/[V1 - Architecture, Design and Threat Modeling Requirements]
* [RiskStatusMitigated]#Cheat Sheet#: https://cheatsheetseries.owasp.org/cheatsheets/Threat_Modeling_Cheat_Sheet.html[Threat_Modeling_Cheat_Sheet]
