[[exposed-default-credentials]]
== [.HighRisk]#Asset Using Known Default or Hardcoded Credentials: 1/1 unmitigated Risk#

*Description* (Information Disclosure): https://cwe.mitre.org/data/definitions/1392.html[CWE 1392]::
Technical assets tagged as intentional-misconfiguration that store confidential data represent an immediately exploitable attack vector. Default credentials (e.g. minioadmin/minioadmin, admin/admin, postgres/postgres) are published in vendor documentation and are the first credentials an attacker tries after reaching the service network.


*Impact*::
Any attacker with network access can authenticate using default credentials, exfiltrate all stored data, modify records, or pivot into adjacent systems.


*Detection Logic*::
In-scope technical assets tagged with intentional-misconfiguration that store data assets rated at confidential or above.


*Risk Rating*::
High severity — default credentials plus confidential stored data equals a trivial full data breach with no exploitation skill required.


[RiskStatusFalsePositive]#*False Positives*#::
[RiskStatusFalsePositive]#Development or ephemeral test environments where no real PII or confidential data is present. Set the asset out_of_scope or remove the intentional-misconfiguration tag once credentials are rotated.
#

[RiskStatusMitigated]#*Mitigation*# (Operations): Rotate all default credentials before deployment; store secrets in a secrets manager::
Replace all default credentials with randomly generated secrets (minimum 32 chars). Store in a secrets manager (Vault, AWS Secrets Manager, etc.) rather than environment variables or compose files. Add credential rotation to the pre-deployment checklist.



* [RiskStatusMitigated]#ASVS Chapter#: https://owasp.org/www-project-application-security-verification-standard/[V2 - Authentication Verification Requirements]
* [RiskStatusMitigated]#Cheat Sheet#: https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html[Authentication_Cheat_Sheet]


*Check*

Are all service credentials rotated from vendor defaults? Are secrets stored in a dedicated secrets manager rather than plain environment variables?

[[cloud-no-audit-logging-high-value]]
== [.ElevatedRisk]#Cloud Audit - High-Value Cloud Service Without Audit Logging: 5/5 unmitigated Risks#

*Description* (Repudiation): https://cwe.mitre.org/data/definitions/778.html[CWE 778]::
High-value cloud services (managed databases, object storage, serverless functions, API gateways) that do not have audit logging enabled make it impossible to detect unauthorized access, investigate breaches, or meet compliance requirements. Cloud audit logs (CloudTrail, GCP Cloud Audit Logs, Azure Monitor) capture who accessed what resource, when, and from where, providing the forensic foundation for incident response.


*Impact*::
Without audit logging, unauthorized access and data exfiltration can go completely undetected. Post-incident forensic investigation is severely hampered. Compliance with GDPR, HIPAA, SOC2, and PCI-DSS typically requires demonstrable audit trails for access to systems processing sensitive or personal data.


*Detection Logic*::
In-scope technical assets with managed-database, object-storage, serverless-function, or cloud-api-gateway technology that process confidential data and are not tagged with has-audit-logging.


*Risk Rating*::
High when the service handles strictly-confidential data. Medium for confidential data without direct regulatory exposure.


[RiskStatusFalsePositive]#*False Positives*#::
[RiskStatusFalsePositive]#Services where audit logging is enforced at the infrastructure level (e.g., via AWS Organizations Service Control Policies) rather than per-service configuration. Tag has-audit-logging after confirming coverage via the centralized policy.
#

[RiskStatusMitigated]#*Mitigation*# (Operations): Enable audit logging on all high-value cloud services and route logs to a tamper-resistant sink::
Enable data plane logging for all high-value cloud services: S3 server access logging, RDS audit log, Lambda invocation logging, API Gateway access logging. Route all logs to a centralized, immutable log sink (CloudWatch Logs with log protection, GCS bucket with object lock). Set up anomaly alerts on admin actions. Tag the asset has-audit-logging once logging is verified.



* [RiskStatusMitigated]#ASVS Chapter#: https://owasp.org/www-project-application-security-verification-standard/[V7 - Error Handling and Logging Verification Requirements]
* [RiskStatusMitigated]#Cheat Sheet#: https://cheatsheetseries.owasp.org/cheatsheets/Logging_Cheat_Sheet.html[Logging_Cheat_Sheet]


*Check*

Is audit logging enabled for all access (read and write) to this high-value service? Are logs shipped to a tamper-resistant centralized log store?

*Description* (Tampering): https://cwe.mitre.org/data/definitions/1104.html[CWE 1104]::
Container platforms running images that are not scanned for known CVEs regularly ship vulnerable base images and application dependencies into production. Container image scanning (Trivy, Snyk, AWS ECR scanning, GCP Artifact Registry scanning) identifies publicly disclosed vulnerabilities in OS packages and language libraries before they are deployed, providing a critical defense-in-depth layer against known exploits.


*Impact*::
Unscanned container images may contain critical or high CVEs with public exploits. An attacker can exploit these vulnerabilities to achieve container escape, privilege escalation inside the container, or lateral movement across the cluster.


*Detection Logic*::
In-scope container-platform technical assets not tagged with has-image-scanning.


*Risk Rating*::
Medium baseline. Elevated to High when the container platform runs internet-facing workloads or processes confidential data.


[RiskStatusFalsePositive]#*False Positives*#::
[RiskStatusFalsePositive]#Container platforms running only pre-hardened, distroless base images from a curated approved list with a separate audit process. Tag has-image-scanning after the alternative scan process is documented.
#

[RiskStatusMitigated]#*Mitigation*# (Operations): Enable image scanning in the container registry and gate deployments on scan results::
Enable automatic vulnerability scanning in the container registry (ECR enhanced scanning, GCR Container Analysis, ACR Defender). Integrate scan results into the CI/CD pipeline and block deployment of images with critical or high CVEs without an accepted exception. Run Trivy or Grype in the CI pipeline as an additional gate. Tag the asset has-image-scanning once scanning is enabled and enforced.



* [RiskStatusMitigated]#ASVS Chapter#: https://owasp.org/www-project-application-security-verification-standard/[V14 - Configuration Verification Requirements]
* [RiskStatusMitigated]#Cheat Sheet#: https://cheatsheetseries.owasp.org/cheatsheets/Docker_Security_Cheat_Sheet.html[Docker_Security_Cheat_Sheet]

== [.ElevatedRisk]#Cloud Container - Container Registry Publicly Accessible: 1/1 unmitigated Risk#

*Description* (Information Disclosure): https://cwe.mitre.org/data/definitions/284.html[CWE 284]::
Container image registries (ECR, GCR, ACR) that are publicly accessible allow any internet actor to pull images from the registry. Container images frequently contain embedded application code, configuration files with connection strings, and in some cases hardcoded secrets. Public pull access also enables an attacker to analyze image layers for vulnerabilities and plan targeted exploits against the production workload.


*Impact*::
Publicly accessible images expose application source code, embedded configuration, and potentially secrets baked into image layers. Attackers can identify unpatched vulnerabilities in the exact versions deployed in production and craft targeted exploits. Images may also contain proprietary business logic.


*Detection Logic*::
In-scope technical assets with container-registry technology that are internet-accessible and not tagged with has-private-registry.


*Risk Rating*::
High when images contain proprietary code or application configuration. Medium for base-image-only registries with no application logic.


[RiskStatusFalsePositive]#*False Positives*#::
[RiskStatusFalsePositive]#Intentionally public open-source project registries serving community images that contain no proprietary code or secrets. Tag has-private-registry after confirming all sensitive images are excluded from the public repository.
#

[RiskStatusMitigated]#*Mitigation*# (Architecture): Restrict container registry access to authenticated principals within the VPC or organization::
Disable public pull access on the container registry. Require IAM authentication for all registry operations. Use VPC endpoint policies to restrict registry access to known VPC CIDRs. Audit existing images for embedded secrets with tools like Trufflehog or Gitleaks. Tag the asset has-private-registry once access is restricted.



* [RiskStatusMitigated]#ASVS Chapter#: https://owasp.org/www-project-application-security-verification-standard/[V8 - Data Protection Verification Requirements]
* [RiskStatusMitigated]#Cheat Sheet#: https://cheatsheetseries.owasp.org/cheatsheets/Docker_Security_Cheat_Sheet.html[Docker_Security_Cheat_Sheet]

[[cloud-managed-db-no-encryption]]
== [.ElevatedRisk]#Cloud Data - Managed Database Without Encryption at Rest: 1/1 unmitigated Risk#

*Description* (Information Disclosure): https://cwe.mitre.org/data/definitions/312.html[CWE 312]::
Managed cloud databases (RDS, Aurora, Cloud SQL, CosmosDB) without transparent data encryption (TDE) store table data, indexes, and backups in plaintext on the underlying storage tier. A provider-side breach, a misconfigured snapshot, or a storage engineer with direct volume access can expose all records. Most compliance regimes (PCI-DSS, HIPAA, GDPR) require encryption at rest for sensitive and personal data.


*Impact*::
Unencrypted database files and their automated snapshots can be mounted and read outside the database engine. Snapshot sharing misconfigurations (a common accidental exposure) bypass all access controls when the data is unencrypted.


*Detection Logic*::
In-scope technical assets with managed-database technology and encryption set to none.


*Risk Rating*::
High when the database holds confidential or strictly-confidential data. Medium for internal data where external exposure risk is low.


[RiskStatusFalsePositive]#*False Positives*#::
[RiskStatusFalsePositive]#Development databases holding only synthetic or public test data. Lower the data asset confidentiality to public or set encryption to transparent to suppress.
#

[RiskStatusMitigated]#*Mitigation*# (Architecture): Enable transparent data encryption on all managed databases storing sensitive data::
Enable encryption at rest on the managed database: RDS/Aurora encrypt-at-rest, GCP Cloud SQL Disk Encryption, Azure SQL Transparent Data Encryption. Prefer customer-managed KMS keys for databases storing strictly-confidential data. Set the asset's encryption field to transparent (or higher) to reflect this state.



* [RiskStatusMitigated]#ASVS Chapter#: https://owasp.org/www-project-application-security-verification-standard/[V6 - Stored Cryptography Verification Requirements]
* [RiskStatusMitigated]#Cheat Sheet#: https://cheatsheetseries.owasp.org/cheatsheets/Cryptographic_Storage_Cheat_Sheet.html[Cryptographic_Storage_Cheat_Sheet]


*Check*

Is encryption at rest enabled on the database instance and its automated snapshots? Are customer-managed keys used for databases with strictly-confidential data?

== [.ElevatedRisk]#Cloud Network - API Gateway Without Rate Limiting: 1/1 unmitigated Risk#

*Description* (Denial of Service): https://cwe.mitre.org/data/definitions/770.html[CWE 770]::
API gateways without rate limiting expose backend services to unbounded request floods that can exhaust serverless invocation quotas, trigger compute autoscaling cost amplification, and overwhelm downstream databases. Rate limiting at the API gateway layer also prevents credential stuffing by throttling high-frequency authentication attempts from individual IP addresses or API keys.


*Impact*::
Without rate limiting, a determined attacker or misconfigured client can trigger denial of service through cost amplification (serverless per-invocation billing), exhaust backend connection pools, or perform credential stuffing attacks at thousands of attempts per second with no automated blocking.


*Detection Logic*::
In-scope cloud-api-gateway technical assets not tagged with has-rate-limiting.


*Risk Rating*::
Medium baseline. Elevated when the gateway fronts serverless functions billed per-invocation, or when it handles authentication endpoints.


[RiskStatusFalsePositive]#*False Positives*#::

#

[RiskStatusMitigated]#*Mitigation*# (Operations): Configure per-client rate limiting on all API gateway routes::
Configure usage plans or throttling policies on the API gateway. Apply per-route and per-API-key rate limits matching the expected legitimate peak load. Add IP-based throttling via WAF for unauthenticated endpoints. Set burst limits to prevent sudden quota exhaustion. Tag the asset has-rate-limiting once configured.



* [RiskStatusMitigated]#ASVS Chapter#: https://owasp.org/www-project-application-security-verification-standard/[V13 - API and Web Service Verification Requirements]

[[cloud-api-gateway-no-waf]]
== [.ElevatedRisk]#Cloud Network - Internet-Facing API Gateway Without WAF Protection: 1/1 unmitigated Risk#

*Description* (Tampering): https://cwe.mitre.org/data/definitions/693.html[CWE 693]::
Cloud API gateways that serve internet traffic without a Web Application Firewall (WAF) have no automated protection against common web exploits including SQL injection, XSS, path traversal, and HTTP floods. A WAF inspects request payloads and headers before they reach backend services, providing a defense-in-depth layer that can block known attack patterns in real-time.


*Impact*::
Without WAF protection, a single successful injection or exploitation of an unpatched vulnerability in a backend service can lead to data exfiltration, authentication bypass, or denial of service. WAF absence also means no geo-blocking or rate-limiting at the edge for volumetric attacks.


*Detection Logic*::
In-scope technical assets with cloud-api-gateway technology that are internet-accessible and not tagged with has-waf.

[RiskStatusMitigated]#*Mitigation*# (Architecture): Attach a WAF (AWS WAF, Azure Front Door WAF, GCP Cloud Armor) to all internet-facing API gateways::
Attach a managed WAF to the API gateway with at minimum the OWASP Core Rule Set enabled. Enable rate-limiting rules to throttle credential stuffing and scraping. Enable logging of all blocked requests. Tag the asset has-waf once the WAF is attached and the rule set is verified in enforcement (not detection-only) mode.

[[cloud-serverless-overpermissive-role]]
== [.ElevatedRisk]#Cloud Serverless - Function Execution Role Without Least-Privilege Restrictions: 1/1 unmitigated Risk#

*Description* (Elevation of Privilege): https://cwe.mitre.org/data/definitions/250.html[CWE 250]::
Serverless functions attached to overly permissive execution roles (e.g., an IAM role with AdministratorAccess or * actions on all resources) violate the principle of least privilege. If the function is compromised via a code injection vulnerability or a supply-chain attack on a dependency, the attacker inherits the full permissions of the execution role, potentially gaining control of the entire cloud account.


*Impact*::
A compromised function with an overpermissive role allows privilege escalation: the attacker can create backdoor IAM users, exfiltrate data from other services, pivot to other accounts, or destroy infrastructure. The blast radius equals the IAM role's permissions scope.


*Detection Logic*::
In-scope serverless function technical assets processing confidential data that are not tagged with has-restricted-execution-role.

== [.LowRisk]#DoS-risky Access Across Trust-Boundary: 3/3 unmitigated Risks#

*Description* (Denial of Service): https://cwe.mitre.org/data/definitions/400.html[CWE 400]::
Assets accessed across trust boundaries with critical or mission-critical availability rating are more prone to Denial-of-Service (DoS) risks.

*Impact*::
If this risk remains unmitigated, attackers might be able to disturb the availability of important parts of the system.

*Detection Logic*::
In-scope technical assets (excluding load-balancer) with availability rating of critical or higher which have incoming data-flows across a network trust-boundary (excluding devops usage).

*Risk Rating*::
Matching technical assets with availability rating of critical or higher are at low risk. When the availability rating is mission-critical and neither a VPN nor IP filter for the incoming data-flow nor redundancy for the asset is applied, the risk-rating is considered medium.

[RiskStatusFalsePositive]#*False Positives*#::
[RiskStatusFalsePositive]#When the accessed target operations are not time- or resource-consuming.#

[RiskStatusMitigated]#*Mitigation*# (Operations): Anti-DoS Measures::
Apply anti-DoS techniques like throttling and/or per-client load blocking with quotas. Also for maintenance access routes consider applying a VPN instead of public reachable interfaces. Generally applying redundancy on the targeted technical asset reduces the risk of DoS.
